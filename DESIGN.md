
# Design

## 0. How I built this (my process)

1. **Understand first.** I gave the assignment to Claude and asked it to make me understand the project before any code:
   what a voice assistant pipeline is (speech-to-text → brain → text-to-speech), and how a "brain" can answer
   without an LLM (a state machine that fills slots, plus fixed reply templates). I picked the dental-clinic use case.
2. **Scenarios before code (first ~30 minutes).** I wrote down how I would really phone the clinic, as a patient's
   relative, including messy cases: changing my mind, a taken slot, a price question and a discount request. These
   calls are in section 1 below. I then turned them into an "arrow table" (state → what the caller says → next state
   → what the assistant says), which is the spec for the brain.
3. **The brain, bottom-up, written by me.** I started with `booking.py` (opening hours, 30-minute grid, double-booking
   protection, next free slots). I asked Claude to **only review** my code and explain my mistakes, not to rewrite
   it. Then I wrote its test file (`test_booking.py`). I did the same for `nlu.py` (normalise, intents, services)
   and `test_nlu.py`. This was the biggest part of my time.
4. **Rest of the brain.** Because of the time limit, the remaining brain code (`extractors.py`, `parser.py`,
   `state.py`, `responses.py`, `policy.py`) and its tests were generated by Claude from my scenarios and arrow table,
   and I then read it, ran it and worked through it to understand it. AI_USAGE.md lists exactly who wrote what.
5. **Backend API and frontend.** I generated the FastAPI layer (sessions, routes, config, CLI) and the whole Next.js
   frontend with Claude, then ran them against my brain and checked a full call in the browser.

## 1. Use case

**Smile Dental Clinic (fictional) — booking a new appointment by phone.**

Why this job: the conversation is *narrow and structured*. A receptionist needs five facts (treatment, day, time,
patient name, phone number) and has to check them against one hard constraint (a calendar). That is exactly the kind of
problem rules solve well and predictably, and it is easy to test.

| In scope | Out of scope (detected, then politely declined) |
|---|---|
| Book: checkup, cleaning, filling, root canal, wisdom-tooth extraction | Cancel or reschedule an existing appointment |
| Answer: prices, opening hours, services, location | Medical advice, insurance, payments |
| Refuse discounts, hand off to a human when stuck | Anything outside the clinic |

Fake data only: clinic name, address, prices, phone numbers and the demo bookings.

### My scenarios (written before any code)

These are the calls I imagined first. Everything in the brain exists to handle them.

**Call 1 — the basic call (clinic time asked in the middle)**

```
me    : hey how are you?
agent : I am good, how are you? What brings you here?
me    : I want to extract one of my mother's wisdom teeth, it is infected
agent : Okay, what is her name and age so I can make an appointment?
me    : her name is Alice and her age is 47, and what is your clinic time?
agent : We are open from 9 am to 6 pm
me    : great, I will be there at 11 am tomorrow
agent : Okay, what is your phone number?
me    : my number is the one I am calling from, or 03123456789
```
*Shows:* one sentence can contain an answer **and** a question (name + clinic time); the question is answered,
then the flow continues.

**Call 2 — the slot is taken, urgent patient, confirmation**

```
me    : I want to extract an infected wisdom tooth of my mother
agent : If it is urgent, tell me when you are available and I will check
me    : what is your time on Saturday?
agent : We work from 9 am to 6 pm on Saturday
me    : are you available at 9 am tomorrow?
agent : Sorry, I have an appointment then. What about 11 am?
me    : sounds good, I will be there at 11 am
agent : What is the patient's name and age?
me    : her name is Alice and her age is 47
agent : And your phone number?
me    : 03123456789
agent : Confirming your appointment at 11 am tomorrow for Alice?
me    : yes, confirmed
agent : Thank you
me    : bye
```
*Shows:* check the calendar; if the time is taken, offer another; confirm; goodbye.

**Call 3 — the caller changes their mind**

I say it is actually for my **father**, not my mother. The agent asks his name; I say Bob. At the confirmation I say
"actually, make it 1 pm". The agent asks to confirm again — "1 pm tomorrow for Bob?" — and I say yes.

*Shows:* newer information overwrites older; a new patient clears the old name; a correction at the confirmation
beats a plain yes/no.

**Call 4 — price and discount**

I ask "what are the charges for molar extraction?" The agent says 10,000 PKR. I say "can you make it 8k?" — the
agent does not understand "8k" as a request and says "sorry, say that again". I ask "why don't you give me a discount
for 8k?" and the agent says it does not have permission to change the price.

*Shows:* "8k" must be read as money, **not** as 8 o'clock; the bot refuses discounts politely; it never invents
prices.

## 2. The big picture

```
 text in ──► normalize ──► NLU ──────────────► POLICY ──────────────► templates ──► text out
              lower-case   intents (phrases)    uses the SESSION       fixed sentences
              no punct.    service (synonyms)   (state + slots)        with {blanks}
                           time/date/phone/     + the CALENDAR
                           name/choice/relation
```

Three layers, each knows nothing about the next:

1. **NLU** (`nlu.py`, `extractors.py`, `parser.py`) turns one sentence into an `NLUResult`: a *set of intents* plus
   any values found. It never decides anything.
2. **Policy** (`policy.py`) looks at the `NLUResult`, the `Session` and the calendar and decides **what to do**
   (which template, which values, which state next).
3. **Responses** (`responses.py`) holds every sentence the assistant can ever say. There is **no text generation**:
   the policy picks a template name and fills its blanks with data from the calendar or the session.

That is why a system without an LLM can still "talk": its vocabulary is small, fixed, and written by a human.

## 3. NLU — how a sentence is understood

* **Normalise:** lower-case, drop apostrophes and dots ("5 P.M." → "5 pm"), other punctuation → space.
* **Intents** are found by whole-word phrase matching (the text is padded with spaces so "hi" does not match
  "this"). A sentence can carry several intents: "hi, what are your timings and I'd like to book" →
  `{greeting, ask_hours, book}`.
* **Service** by a synonym table ("tooth removal", "extraction", "wisdom tooth" → `wisdom tooth extraction`).
* **Time** rules: `5:30`, `5 pm`, "half past four", "quarter to five", "noon", "at 9", and the *clinic rule* for a bare
  hour: 1–8 means PM, 9–12 stays, an explicit am/pm always wins. A bare number ("5") is only a time when the
  assistant has just asked for a time (`expecting` hint from the state).
* **Money is not a time:** "8k" / "8000 rupees" are recognised first, so "make it 8k" never becomes 8 o'clock.
* **Date:** today, tomorrow, day after tomorrow, weekdays (next occurrence after today), "27 October", "October 27 2026".
  `today` is passed in so tests can freeze it.
* **Phone:** 10–13 digits, tolerating spaces, dashes and spoken digit words.
* **Name:** explicit patterns ("my name is…", "this is…") or a bare word *only when the assistant just asked for a name*;
  a blocklist built from the intent/service phrases stops "tomorrow" or "cleaning" becoming a name.
* **Choice** ("the second one" → 2) and **relation** ("for my father" → `father`).

## 4. Policy — how the brain decides

The brain is a **state machine with slot filling**: like a receptionist with a clipboard. The *state* is the question
we are currently waiting for an answer to; the *slots* are the clipboard fields.

States: `ASK_SERVICE`, `ASK_WHEN`, `OFFER_ALTERNATIVE`, `ASK_PATIENT`, `ASK_PHONE`, `CONFIRM`, `DONE`.

Every caller turn runs the same pipeline:

1. **Nothing understood?** count a failure: 1 → "sorry, didn't catch that" + re-ask; 2 → same + an example sentence;
   3 → hand off to the front desk. Understanding anything resets the counter.
2. **Global intents**, valid in every state: goodbye (end, book nothing), "talk to a person" (hand off), repeat (say the
   last reply again).
3. **Side questions** — price, hours, services, location, discount, urgent, cancel/reschedule — are answered, and then
   **the pending question is asked again**, so the caller never loses their place. A service/date/time that appears
   inside a *question* ("how much is a cleaning?") is information to look up, not a booking choice, and is not saved.
4. **State-specific input:**
   * `OFFER_ALTERNATIVE`: "the second one" → that slot; a plain "yes" → the first; a new time → validate it; "no" → ask again.
   * `CONFIRM`: **a correction beats yes/no.** "Yes, but make it 1 pm" changes the time and asks to confirm again.
     A bare "yes" books; a bare "no" asks what to change.
5. **Update slots** — newer information overwrites older ("actually Friday"). If the caller says a *different relation*
   ("sorry, it's for my father" after "my mother"), the old patient name is forgotten and asked for again.
6. **Validate the requested time**, in this order: date in the past → closed day → time in the past → not on the
   30-minute grid → outside opening hours → already taken. Every failure except "in the past" offers the next three free
   slots from the calendar. Opening hours come from one table (`OPENING_HOURS`), used both to enforce and to *speak*
   ("Monday to Saturday, 9:00 AM to 5:00 PM; closed on Sunday"), so the two can never disagree.
7. **Go to the first empty slot:** service → date+time → patient name → phone → `CONFIRM`.

The booking itself is the only action with a side effect. If someone else took the slot while the caller was talking,
`SlotTakenError` is caught and new slots are offered instead of failing.

### Decisions worth knowing

| Decision | Reason |
|---|---|
| The brain never agrees to a discount | A phone bot has no authority to change prices. 1st ask: polite refusal. 2nd ask: firmer refusal + offer to book at the standard fee. |
| A bare hour 1–8 means PM | A dental clinic that is open 9–5 is never booked for 3 AM; fewer clarifying questions. |
| "Urgent / pain" → offer the earliest slots (30 min from now) | Quickest useful outcome for someone in pain. |
| Cancel / reschedule detected but not performed | Honest scope: better to say "call the front desk" than to half-implement it. |
| Phone numbers are read back digit by digit | Voice output reads "0 3 1 2…" clearly. |
| After 3 misunderstandings, hand off | A looping bot is worse than no bot. |

## 5. Reliability

* **Time is injected** (`clock=`), so every test is deterministic.
* **Double-booking protection** lives in the calendar (`book()` validates grid → hours → service → free), not in the
  brain; the API test books the same slot from two sessions and checks the second caller is re-offered other times.
* **Input limits:** text length 1–500 characters; unknown sessions return 404; CORS only for configured origins.
* **Tests:** unit tests for every extractor and the calendar, ~20 *whole-call scenario* tests (the acceptance tests for the
  policy), API tests with FastAPI's `TestClient`, and small frontend unit tests.

## 6. What I would do next

* Persist the calendar and sessions (SQLite/Postgres + Redis) and add cancel/reschedule.
* Put a telephony provider in front (the brain only needs text in / text out).
* Use the speech recogniser's alternative transcripts and confidence to ask for confirmation of low-confidence phone numbers.
* Add Urdu/Roman-Urdu phrase lists (the phrase tables are plain data, so this is mostly adding words).
* Log anonymised "not understood" sentences to grow the phrase lists from real calls.
